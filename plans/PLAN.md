## 0. Document control and start protocol

### 0.1 Precedence and change control

- After E1 is signed off, files in `spec/` and `conformance/` win over this file where they conflict. A conflict is a spec bug: file a change request (section 16.4).
- Do not edit this file to make a failing check pass. Edit it only through an accepted change request, which bumps the version line.

### 0.2 Start protocol (every agent, every session)

1. `cd` to the repo root. Run `git status` and `git log --oneline -5`. If the repo is not initialized, only E0 may run.
2. Read `STATUS.md` (generated, section 16.3). Find your role's rows.
3. Read sections 0, 1, 2 and 14. Then read your role's milestones in section 15, then the sections they reference.
4. Read `spec/CHANGE_REQUESTS.md` for open items that touch your milestone.
5. Work only on the first milestone in your role's list whose state is `todo` or `doing` and whose dependencies are `done`. Set it to `doing` in your status file before starting.
6. When finished, run the milestone's verify command, save output (rule 2.5), commit, set state to `verify`, and stop. Spec/Conformance moves it to `done`.

### 0.3 Roles

| Role | Purpose |
|---|---|
| Spec/Conformance | Freeze the protocol and policy, write conformance cases before any implementation, verify other roles' milestones in a fresh clone |
| Core | The engine: store, index, policy, protocol server, CLI |
| Bindings | Language clients over the protocol: Node (first-class), Python (later) |
| Adapters | Recorders and planners: Vitest, native `strace` oracle, git change sources, MCP server |
| Bench | Harness, baselines, replay, gate numbers |

In single-agent mode one agent plays them in order. The conformance cases are committed before any Core or Bindings code (rule 2.2), and that ordering is the only independence between spec and code.

## 1. Mission, scope, name

### 1.1 What backplane is

backplane is an **incremental dependency engine**. It records what each task reads, lists, probes and writes, stores those observations as content-hashed records, and answers one question: *given these changes since the last known-good baseline, which tasks are invalid, and why?*

The engine has no opinion about tests, builds or CI. Those are **adapters**. The engine exposes a stable protocol, so any language, runner or agent can use it.

### 1.2 Mission

1. **Save time without losing correctness.** Skip work only when a recorded observation proves the work's inputs have not changed. Gate in section 13.
2. **Never skip silently.** Unknown, unverifiable or unrecorded input means the task is invalid, and the reason says so. Zero false skips is the target; the measured value is reported with a confidence bound (section 12.6).
3. **Be usable from anywhere.** Stable protocol, typed bindings, a CLI, and an agent interface.

### 1.3 Scope

**In scope for v1:**

- The engine: observations, store, index, policy, baseline management, plans, explanations.
- Protocol v1 over JSON Lines on stdio, and a CLI.
- Bindings: Node/TypeScript (typed client). Python is a later milestone.
- Adapters: Vitest (test files as tasks), a Linux `strace` recorder (oracle and fallback), git change sources, and an MCP server.
- Conformance suite that any core implementation must pass.

**Non-goals for v1:**

- Running tasks as a product. Adapters run them, and the engine only decides what needs running.
- Build caching and artifact storage. Turborepo and Nx own that. backplane may later provide build-input observations to them (section 4.3), but not outputs.
- Production observability, distributed execution, Windows, a GUI.
- Remote or shared stores beyond the per-worktree default (D-11).
- Non-file inputs such as time, network and randomness, which are recorded as a stated limit (section 9.6).

### 1.4 Name

**backplane** is the working name. As of 2026-11-03, npm has no package named `backplane`, and the scope `@backplane` was not checked. Trademark, GitHub organization and domain availability were **not** checked; that is milestone E0 step 1. All package names and CLI names are defined in one place (section 10.5), so a rename changes one file.

## 2. Ground rules for every agent

1. A milestone is done only when its verify command passes, its output is saved to `evidence/<id>.txt`, and the work is committed as `<id>: <deliverable>`.
2. **Specification before implementation.** Conformance cases and protocol schemas are written and committed first. Core and Bindings MUST NOT edit `spec/` or `conformance/cases/`. Request changes in `spec/CHANGE_REQUESTS.md`.
3. Never weaken a test, change a benchmark target, or edit the gate after seeing results. If a check fails, fix the code, or report that the check is wrong.
4. Never skip silently. Unknown or unverifiable input means the task is invalid (or the whole plan falls back, per section 8.2).
5. Never claim success without running the command and reading its output. Paste the final ten lines into the evidence file.
6. Log surprises. `friction/FRICTION.md` for tool or language obstacles, `DECISIONS.md` for choices this spec does not make, `VERSIONS.md` for exact versions. These three are append-only (section 16.2).
7. Edit only the paths your role owns (section 16.1). Cross-role needs go through change requests.
8. The core engine MUST stay under 8,000 lines excluding tests and generated code. Check with `make loc`. Passing that is a stop condition.
9. Dependencies. Core: only what D-14 allows. Bindings: the language's standard library plus the protocol. Adapters: `vitest`, `typescript`, the official MCP SDK, `ajv` for schema checks, `hyperfine` (benchmarks tool only). Anything else needs a `DECISIONS.md` entry.
10. Do not run anything that needs credentials or paid services. Do not install software outside the repo, except the toolchain listed in E0. Anything else is a stop condition.
11. Pin every version in `VERSIONS.md` with the exact version. **A pin must be at least 14 days old on the day it is pinned**, unless a `DECISIONS.md` entry explains the exception.
12. Every `make` target prints a final line `PASS <target>` or `FAIL <target>`, and exits 0 or nonzero accordingly. Definitions are in section 17.1.
13. **Units.** Time in milliseconds unless stated. Sizes in bytes. Paths are repo-relative with `/` separators. Hashes are `sha256:<lowercase hex>`. Timestamps are RFC 3339 UTC. Identifiers are UTF-8 strings.

## 3. Model

These definitions are normative. Every protocol message, log record and policy rule uses these terms.

### 3.1 Terms

| Term | Meaning |
|---|---|
| **Task** | A named unit of work the engine tracks. Identified by a string `id`. Vitest adapter: a test file. A build adapter might use a package and target. |
| **Input** | Something a task depends on. Kinds below. |
| **Output** | A file a task produces. Recorded for explanation and future cache use; not used for invalidation in v1. |
| **Observation** | One recorded run of a task: its inputs, outputs, outcome, the baseline it was taken at, and whether the worktree was dirty. |
| **Baseline** | An opaque string naming the state the graph is valid for. For git repos: a commit SHA. The engine compares strings only. |
| **Context** | The environment a task was observed in: tool versions, lockfile hash, and an env snapshot. Stored with each observation. |
| **ChangeSet** | The changes between a baseline and the current state, given as path and status entries. |
| **Plan** | The engine's answer to a query: which tasks are invalid, why, what is unknown, and the confidence. |
| **Certificate** | The positive evidence that makes a skip safe: an observation at the baseline in which the task read, listed, probed or depended on nothing that changed. |

### 3.2 Input kinds

| Kind | Fields | Meaning |
|---|---|---|
| `file` | `path`, `hash` | The task read this file (content at observation time) |
| `dir` | `path` | The task listed this directory. Any change to its entries matters |
| `probe` | `path` | The task looked for this path and it did not exist. Creating it matters |
| `env` | `name`, `value_hash` or `"unset"` | The task read this environment variable |
| `env_all` | none | The task enumerated the whole environment. Any change matters |
| `declared` | `path` | The adapter declared this file as an input without observing a read (for example a config file known to matter). Treated like `file` |

### 3.3 The certificate principle

> A task may be skipped only if it has a certificate: an observation, valid at the current baseline, whose inputs are all unchanged.

Everything in section 8 follows from this. If a task has no certificate, it is invalid. A fallback exists for the cases where the engine cannot even tell which tasks lack one.

### 3.4 Baseline invariant

Let `B` be the store's current baseline. The invariant is:

> Every task's latest observation is valid at `B`: every change between that observation's baseline and `B` was checked against that task by a query whose baseline was the previous one.

Consequences the design enforces:

- Advancing the baseline is an explicit operation (`advance`) that the adapter calls after a clean run. It takes the previous baseline as `expected`, so two writers cannot silently skip each other's changes (section 9.4).
- A query must name its baseline. If it differs from `B`, the result is a fallback `baseline_mismatch`. The engine does not guess across mismatches.
- A multi-step change (several commits) is covered because the adapter computes changes from `B`, not from the previous commit.

## 4. Architecture

```
  consumers                    adapters                       bindings
  ─────────                    ────────                       ────────
  CI scripts                   vitest  (recorder + planner)   Node client  (typed)
  MCP agents  ─────────┐       strace  (native recorder)      Python      (later)
  humans (CLI)         │       git     (change source)        CLI  backplane
                       ▼           │                              │
               ┌──────────────────────────────────────────────────────┐
               │   backplane Protocol v1  (JSON Lines over stdio)      │
               └──────────────────────────────────────────────────────┘
                                       │
               ┌──────────────────────────────────────────────────────┐
               │   Engine core: store · index · policy · plans        │
               │   store dir: tg.log · tg.idx · tg.lock · stat.cache  │
               └──────────────────────────────────────────────────────┘
```

Layering rules:

- **Core** knows inputs, outputs, observations, baselines and policy. It knows nothing about Vitest, git or tests.
- **Protocol** is the only way bindings and tools reach the core, with one exception: the CLI, which is a thin binding over the same messages.
- **Adapters** translate their world into observations and plans. A recorder produces observations; a planner turns a plan into work for its tool.

### 4.1 Decisions

Changing one needs a `DECISIONS.md` entry and Spec/Conformance approval.

- **D-1 Protocol boundary.** Every consumer reaches the core through the protocol. No binding links the core directly in v1. A C ABI is a later option (section 10.6).
- **D-2 Task identity.** Adapters choose task ids. Ids MUST be stable across runs and derived from repo-relative paths or targets, never from absolute paths, process ids or timestamps.
- **D-3 Hash.** SHA-256 over file contents, `sha256:<hex>`, computed by the recorder at record time. The core hashes only in verify mode and for the stat cache.
- **D-4 Canonical store.** The append-only log is the source of truth. The index is a disposable cache.
- **D-5 Identity.** Repo-relative paths plus content hashes. No absolute paths in the log. **mtimes never enter the log.** They live only in the local `stat.cache` (section 7.6).
- **D-6 Two recorders.** The Node recorder (Vitest preload) is the default and portable. The `strace` recorder (Linux) is the oracle that tests the Node recorder's completeness, and a fallback for native tools.
- **D-7 The core never runs git.** The git change source is an adapter that builds the ChangeSet and passes it in. Core takes baselines as opaque strings.
- **D-8 Negative dependencies are first-class.** Probes and directory listings are recorded, so additions can be handled without re-running everything.
- **D-9 Baseline invariant** (section 3.4) is the soundness basis for every skip.
- **D-10 Dirty state.** Observations recorded from a worktree with uncommitted changes are `dirty` and are never trusted for skips (rule P8).
- **D-11 Stores are per worktree by default** (`<repo>/.backplane`). Sharing one store across worktrees is supported; baseline mismatches then fall back, so sharing is safe but often falls back. Documented in the README.
- **D-12 Vitest pool.** Recording requires the Vitest `forks` pool so test code runs in child processes that inherit `NODE_OPTIONS`. Confirmed in Vitest's docs (2026-11-03) as `vitest --pool=forks` and `test: { pool: 'forks' }`. The forks worker starts each file with `child_process.fork()` and passes an explicit `env`, so E4 MUST prove that `NODE_OPTIONS` reaches it.
- **D-13 Protocol versioning.** Protocol v1 is the first. Any breaking change bumps the major version. The client and server negotiate in the `hello` handshake (section 9.2).
- **D-14 Core language (default: TypeScript).** The v1 core is TypeScript on Node LTS, because it runs next to the recorders, ships through npm, and has no compiler risk on the critical path. A Goose core is an optional track (Appendix D). It is accepted only if it passes the same conformance suite and the parity gate (G6). Choosing a different default needs a `DECISIONS.md` entry and a human decision.

### 4.2 Why the protocol is the product boundary

The protocol and the conformance suite are what make the engine real. A second implementation, in Goose or Rust or anything else, has to pass the same cases with byte-identical plans. The core language can change without changing a single adapter.

### 4.3 Adapters in scope and out of scope

| Adapter | Status | Role |
|---|---|---|
| `vitest` | v1 | Recorder and planner for test files |
| `strace` (Linux) | v1 | Native recorder: oracle for the Node recorder, and a fallback for native tools |
| `git` | v1 | ChangeSets from `B` to the worktree, including untracked files and renames |
| `mcp` | v1 (E8) | Agent interface over the Node client |
| `tsc`, bundler inputs | later | Observed build inputs for Turborepo or Nx cache keys; no build outputs stored |
| `ci` | later | Job planning from plans |
| `pytest`, others | later, separate decision | Non-JavaScript ecosystems |

## 5. Engine behavior: summary of guarantees

These guarantees are what the conformance suite checks.

| # | Guarantee |
|---|---|
| G-a | A task without a certificate is never skipped. |
| G-b | A query whose baseline is not the store's baseline never returns a partial plan. It returns the full fallback. |
| G-c | A query without a context returns the full fallback. |
| G-d | Plans are deterministic: identical store and input give identical bytes, independent of input order. |
| G-e | An unknown record in the log is skipped, and a truncated final line is ignored. Neither changes any answer. |
| G-f | The same plan results whether the index is loaded from cache, rebuilt, or updated from the log delta. |
| G-g | Advancing the baseline requires the expected previous value. A mismatch is an error, not a silent overwrite. |

## 6. Data model: log, context, baseline

### 6.1 Canonical log

File `<store>/tg.log`: UTF-8 JSON Lines, append-only. Format version 1.

```
{"r":"hdr","v":1,"hash":"sha256","created":"2026-11-03T10:00:00Z"}
{"r":"context","cid":3,"fields":{"lockfile":"sha256:...","tsconfig":"sha256:...","pkgjson":"sha256:...","runner":"vitest@4.1.12","node":"22.11.0","fmt":1,"caps":{"probes":true,"dirs":true,"env":true}}}
{"r":"path","id":5,"path":"packages/core/src/math.ts"}
{"r":"fv","id":17,"path":5,"hash":"sha256:..."}
{"r":"task","id":"packages/core/src/math.test.ts"}
{"r":"obs","task":"packages/core/src/math.test.ts","cid":3,"baseline":"9f2c1ab...","dirty":false,"inputs":[{"k":"file","fv":17},{"k":"dir","p":9},{"k":"probe","p":40},{"k":"env","name":"TG_FIXTURE_MODE","vh":"sha256:..."}],"outputs":[],"outcome":"pass","ms":412,"at":"2026-11-03T10:00:03Z"}
{"r":"forget","task":"packages/core/src/old.test.ts"}
{"r":"baseline","value":"9f2c1ab...","at":"2026-11-03T10:00:04Z"}
```

Record types:

- `hdr`: format version and hash algorithm. Must be the first line.
- `context`: a context id and its fields. Fields are free-form, but the keys in section 8.4 are reserved.
- `path`, `fv`: interned path ids and file versions (a path id plus a content hash). A `path` or `fv` line MUST precede its first use.
- `task`: declares a task id. Optional; an observation also declares its task.
- `obs`: an observation. `inputs` use compact keys (`k`, `fv`, `p`, `name`, `vh`) to keep the log small. `outcome` is `pass`, `fail`, `error` or `none` (no run result, for example a planned task that was not run).
- `forget`: removes a task from the graph until its next observation.
- `baseline`: sets the store's baseline. The latest `baseline` line is `B`.

Rules:

- Ids are assigned by the writer and unique within a log.
- Readers MUST ignore a truncated final line and MUST skip unknown `r` values. Both are conformance cases (C36, C37).
- The latest `obs` per task wins. A later `forget` removes the task until its next `obs`.
- `graph_version` is `g_` plus the first 8 hex characters of SHA-256 over the log length in bytes (decimal ASCII), then the last 1,024 bytes of the log. Spec/Conformance defines it exactly in `spec/FORMAT.md`.

### 6.2 Context

A context is the environment of an observation. Its fields are compared at query time. The fields reserved by the engine are listed in section 8.4. Adapters MAY add fields. An adapter-added field is compared only if the adapter lists it in `fallbackContextKeys` (section 6.7), otherwise it is compared per task.

### 6.3 Local state (never in the log)

- `<store>/stat.cache`: JSON object mapping `path` to `{size, mtime_ns, hash}`. Written only by verify mode. Deleting it is always safe.
- `<store>/tg.lock`: exclusive-create lock file, content `{"pid": N, "start": "<process start time>"}`. Takeover is allowed only if the PID is not alive or its start time differs (PID reuse).

### 6.4 Index image (cache)

File `<store>/tg.idx`: a sequence of length-prefixed sections. The first is a JSON header `{fmt, base_log_len, base_tail_sha, base_postings, delta_postings}`, where `base_tail_sha` is SHA-256 of the 1,024 log bytes ending at `base_log_len`. Each further section is a binary array image of one base structure from section 6.5. Arrays are growable so they can be restored.

Load:

1. Verify each section. Any failure means full rebuild.
2. If the log is shorter than `base_log_len`, or its bytes ending at `base_log_len` do not hash to `base_tail_sha`, the log was rewritten. Full rebuild.
3. Otherwise replay the log bytes after `base_log_len` into the **delta layer**. This is the incremental reload used by `serve`.
4. When `delta_postings` exceeds 5% of `base_postings`, rebuild the base from the full log.

Writes are write-to-temp then atomic rename. The fallback when the binary image cannot be used is always a full rebuild from the log, which is slower but correct.

### 6.5 In-memory structures

Base layer, flat arrays only:

- Interned path table: path id to string, with the strings stored as one byte blob plus an offsets array (no arrays of variable-size elements).
- Tasks table: task id to name, latest outcome, context id, latest baseline, dirty flag, and offsets into the task's input list.
- Three reverse indexes keyed by path id, each as `offsets: u32[nPaths+1]` and `postings: u32[]` (sorted task ids): **file reads**, **dir listings**, **probes**.
- Per-task forward lists: file inputs with hashes, env inputs, and flags, used for verify and explanations.
- Query scratch: `mark: u32[nTasks]` with an epoch counter. A `u32` epoch wraps after about four billion queries; on wrap, clear the array once. A `u8` epoch is forbidden.

Delta layer: small maps for tasks and postings changed since the base was built. A delta entry overrides the base entry for the same task.

Query cost is the sum of the posting-list lengths touched by the changes, plus the size of the env check set. It does not scale with the total task count.

### 6.6 Concurrency

- One writer at a time through `tg.lock`. Readers never lock.
- Readers tolerate a truncated final line.
- Index swaps are atomic renames.
- Two writers serialize. Conformance and integration tests cover it (E2).

### 6.7 Configuration

`backplane.config.json` at the repo root. Shape:

```json
{
  "roots": ["."],
  "exclude": ["**/node_modules/**", ".git/**", ".backplane/**"],
  "ignore": [],
  "globalInputs": ["pnpm-lock.yaml", "package-lock.json", "yarn.lock", "package.json",
                   "tsconfig*.json", "vitest.config.*", "vite.config.*"],
  "policy": "balanced",
  "fallbackContextKeys": ["lockfile", "tsconfig", "pkgjson", "runner", "node", "fmt", "caps"],
  "adapters": {
    "vitest": { "testGlobs": ["**/*.{test,spec}.{ts,tsx,js,jsx,mjs,cjs,mts,cts}"] }
  }
}
```

`exclude` is matched against **canonical** (realpath) paths only (section 11.4). Globs support `*`, `**` and `?`. `policy` is `balanced` or `conservative`.

## 7. Store lifecycle

### 7.1 First use

`backplane init` creates `<store>/tg.log` with a header and no baseline. The first run of an adapter has no baseline and runs every task (fallback `baseline_mismatch`, because `B` is null). It then advances the baseline.

### 7.2 Steady state

The adapter loop (section 10.4): get `B`, build the ChangeSet from `B` to the worktree, query, run the invalid tasks while recording, and advance `B` to HEAD only if the worktree was clean and every invalid task ran.

### 7.3 Forgetting

Tasks whose definition disappeared are forgotten by the adapter after a query reports them in `deleted_tasks` (rule P5). `forget` appends a record, so the log stays append-only.

### 7.4 Compaction

`backplane compact` rewrites the log keeping live observations, the latest baseline, and the context records still referenced. It writes to a temp file and renames it. Any index built from the old log is invalidated by the tail hash (section 6.4).

### 7.5 Corruption

A corrupt index is rebuilt from the log. A corrupt log record that is not a truncated tail is an error (`store_corrupt`, exit 3); the engine never guesses around it.

### 7.6 Verify and the stat cache

Verify mode checks that recorded file contents still match. For each recorded `(path, hash)`: stat the file. If size and `mtime_ns` equal the cache entry, reuse the cached hash. Otherwise hash the file, update the cache, and compare. Verify is O(recorded files), so it is for CI, audits and shared stores, not the warm path.

## 8. Policy

### 8.1 Procedure

```
plan(changes, options):
  if options.baseline != store.baseline:                  return fallback(baseline_mismatch)     P0
  if options.context is missing:                          return fallback(context_missing)       P0b
  drop changes matching ignore                                                                   P11
  if any change matches globalInputs:                     fallback_codes += global_input         P1
  if a reserved or listed context key differs:            fallback_codes += context_changed      P2
  if fallback_codes nonempty:                             return fallback(highest priority)
  caps = caps of the context
  invalid = {}; unobserved = []; deleted = []
  for c in changes:
    if c.status in (deleted, renamed):
       invalid[readers(old)]   += removed_read:<old>                                             P5
       invalid[dir_readers(parent(old))] += removed_listed:<dir>
       if old is a known task: deleted.add(old)
    if c.status == deleted: continue
    p = c.path
    if p in file_index:           invalid[readers(p)] += reads:<p>                              P3
    if p is a task definition for a known task and status in (added, modified):
                                  invalid[p] += self_changed                                    P4
    elif p not in file_index and status in (added, renamed):
         if policy == balanced and caps.probes and caps.dirs:
              invalid[probe_readers(p)] += probe:<p>; invalid[dir_readers(parent(p))] += dir:<dir>   P6
         else: return fallback(unobserved_input)
    elif p not in file_index and status == modified:
         if policy == balanced and caps.probes and caps.dirs: unobserved.add(p)                 P7
         else: return fallback(unobserved_input)
  for each task t (not forgotten):
    if no observation or latest.dirty:                    invalid[t] += no_observation | dirty_observation        P8
    if latest.outcome in (fail, error):                   invalid[t] += failed_outcome           P9
    for (name, vh) in t.env: if current_env[name] != vh:  invalid[t] += env_changed:<name>       P2b
    if t.env_all and any env differs:                     invalid[t] += env_all_changed          P2b
  if options.verify:
    for each (t, path, hash) in latest observations: check stat cache, then hash; mismatch or missing: invalid[t] += stale:<path>   P10
  return plan(invalid, unobserved, ignored, deleted, skipped = total - |invalid|, confidence)
```

Notes:

- P3 and P4 can both fire for a modified task file: it reads itself. Both reasons are listed.
- P2b uses only env names that tasks recorded. The client sends the full environment hash map, so the core never reads the process environment.
- P10 detects content drift in recorded files only. It does not detect new reads. The baseline invariant (section 3.4) covers new reads.

### 8.2 Rule table

| ID | Condition | Action | Reason code | Was (tg v3) |
|---|---|---|---|---|
| P0 | Query baseline differs from store baseline | Fallback | `baseline_mismatch` | R0 |
| P0b | Context missing | Fallback | `context_missing` | R0b |
| P11 | Changed path matches `ignore` (applied first) | Drop, list in `ignored` | none | R11 |
| P1 | Changed path matches `globalInputs` | Fallback | `global_input` | R1 |
| P2 | A reserved or listed context key differs from the latest recorded context | Fallback | `context_changed` | R2 |
| P2b | A task's recorded env name changed, or `env_all` and any env changed | Select the task | `env_changed:<NAME>` or `env_all_changed` | R2b |
| P3 | Changed path is a file input of some task | Invalidate those tasks | `reads:<path>` | R3 |
| P4 | Changed path is a known task's definition file (adapter-declared) and status is added or modified | Invalidate it | `self_changed` | R4 |
| P5 | Path deleted, or a rename's old path | Invalidate readers (`removed_read`) and dir listers (`removed_listed`). A deleted task definition is listed in `deleted_tasks` and not invalidated | as stated | R5 |
| P6 | Path added or renamed-to, not a file input of any task | `balanced` with caps: invalidate probers (`probe`) and dir listers (`dir`). Otherwise fallback | `unobserved_input` | R6 |
| P7 | Modified path, not a file input, not a task definition | `balanced` with caps: list in `unobserved`. Otherwise fallback | `unobserved_input` | R7 |
| P8 | Task has no observation, or latest is dirty | Invalidate | `no_observation` or `dirty_observation` | R8 |
| P9 | Latest outcome is `fail` or `error` | Invalidate | `failed_outcome` | R9 |
| P10 | `verify` on and a recorded `(path, hash)` no longer matches, or the file is missing | Invalidate | `stale:<path>` | R10 |

### 8.3 Reason code grammar

Reasons are strings: `<code>` or `<code>:<argument>`. The argument is a repo-relative path, a directory path, or an env name. Each reason list is sorted lexicographically. Codes: `reads`, `self_changed`, `removed_read`, `removed_listed`, `probe`, `dir`, `no_observation`, `dirty_observation`, `failed_outcome`, `stale`, `env_changed`, `env_all_changed`, `declared`, `fallback`. Under a fallback, every known task has reason `["fallback"]`.

`declared:<path>` is produced by P3 when the matched input has kind `declared`. It lets an adapter explain a skip or invalidation that came from a declared input.

### 8.4 Reserved context keys

`lockfile`, `tsconfig`, `pkgjson`, `runner`, `node`, `fmt`, `caps`. Their meaning is fixed by the engine. `caps` is an object with boolean fields `probes`, `dirs`, `env`, recording what the recorder can observe. A context whose `caps` lack `probes` or `dirs` cannot use P6 or P7 in balanced mode, so its unobserved adds fall back.

### 8.5 Fallback priority

If several fallback codes fire, the plan reports the highest:
`baseline_mismatch` > `context_missing` > `global_input` > `context_changed` > `unobserved_input`.

### 8.6 Confidence

- `n/a` when a fallback fired.
- `high` only when no fallback fired, `verify` is on, and no task was invalidated for `no_observation`, `dirty_observation` or `stale`.
- `medium` otherwise.

Default queries run without verify, so default output is `medium` unless the adapter opts into verify. This is deliberate: the default does not claim more than it checks.

### 8.7 Edge cases

- **Deleted task definition still in the graph (CR-002).** P5 invalidates every reader of the deleted path, including the deleted task itself when it reads its own file (spec/POLICY.md P5 governs, PLAN 0.1). The deleted task is also listed in `deleted_tasks`. The adapter forgets it after the query.
- **Renamed task definition.** The old id follows P5. The new id has no observation, so P8 invalidates it.
- **Empty ChangeSet.** Only P8, P9 and P2b can invalidate. The plan may be empty.
- **Dirty observations** (P8) are invalidated on every query until a clean run replaces them. This over-invalidates on purpose.

## 9. Protocol v1

### 9.1 Transport and envelope

One JSON object per line in each direction, flushed per line. Requests carry an integer `id` that the response echoes.

```
-> {"id":1,"method":"hello","params":{"protocol":1,"client":{"name":"backplane-node","version":"0.1.0"}}}
<- {"id":1,"result":{"protocol":1,"engine":{"name":"backplane-core-ts","version":"0.1.0"},"capabilities":["probes","dirs","env","verify"],"store":".backplane"}}
-> {"id":2,"method":"affected","params":{...}}
<- {"id":2,"result":{...Plan...}}
<- {"id":3,"error":{"code":"baseline_conflict","message":"expected baseline 9f2c, store has 3e8d","data":{"expected":"9f2c","actual":"3e8d"}}}
```

Responses carry exactly one of `result` or `error`. A malformed line gets an `invalid_params` error with `id: null`, and the loop continues.

### 9.2 Handshake

`hello` MUST be the first request. The server replies with the protocol version it speaks and its capabilities. If the client's `protocol` is not supported, the server replies with `protocol_mismatch` and the list of supported versions, and closes the stream.

### 9.3 Methods

| Method | Params | Result | Notes |
|---|---|---|---|
| `hello` | `{protocol, client}` | `{protocol, engine, capabilities, store}` | First call |
| `observe` | `{observation}` | `{accepted: true}` | Observation schema in 9.5 |
| `observe_many` | `{observations: [...]}` | `{accepted: n}` | Atomic: all or none |
| `baseline` | none | `{baseline: string or null}` | |
| `advance` | `{to, expected}` | `{baseline}` | `expected` must equal the current baseline, else `baseline_conflict` |
| `affected` | `{changes, options}` | Plan (section 9.6) | `changes` is a ChangeSet (9.5). `options`: `{baseline, context, verify, policy}` |
| `explain` | `{task}` | Explanation | Latest observation summary and certificate status |
| `forget` | `{task}` | `{forgotten: true}` | |
| `stats` | none | Stats | Counts, `graph_version`, sizes |
| `compact` | none | `{before_bytes, after_bytes}` | |
| `ping` | none | `{pong: true}` | |
| `shutdown` | none | `{bye: true}` | Server exits after replying |

### 9.4 Baseline and concurrency

`advance` is compare-and-set. The adapter sends the baseline it believes is current as `expected`. A mismatch returns `baseline_conflict` and changes nothing. This is how two adapters running against one store avoid silently skipping each other's changes.

`observe` and `observe_many` do not check the baseline. An observation records the baseline it was taken at, and the policy handles the mismatch when a later query runs.

### 9.5 Schemas (summary; full schemas in `spec/schemas/`)

**Observation**

```json
{
  "task": "packages/core/src/math.test.ts",
  "baseline": "9f2c1ab4e0d7c3a1b2c3d4e5f60718293a4b5c6d",
  "dirty": false,
  "context": { "lockfile": "sha256:...", "tsconfig": "sha256:...", "pkgjson": "sha256:...",
               "runner": "vitest@4.1.12", "node": "22.11.0", "fmt": 1,
               "caps": { "probes": true, "dirs": true, "env": true } },
  "inputs": [
    { "kind": "file", "path": "packages/core/src/math.ts", "hash": "sha256:..." },
    { "kind": "dir", "path": "packages/app/plugins" },
    { "kind": "probe", "path": "packages/core/src/helpers.ts" },
    { "kind": "env", "name": "TG_FIXTURE_MODE", "value_hash": "sha256:..." }
  ],
  "outputs": [],
  "outcome": "pass",
  "duration_ms": 412
}
```

Rules: `task` and `baseline` are required. `context` is required and must contain the reserved keys. `outcome` is `pass`, `fail`, `error` or `none`. Inputs are not sorted by the client; the engine sorts them.

**ChangeSet**

```json
{
  "baseline": "9f2c1ab4e0d7c3a1b2c3d4e5f60718293a4b5c6d",
  "head": "3e8d5a0c1f2b3c4d5e6f708192a3b4c5d6e7f809",
  "changes": [
    {"path": "packages/core/src/math.ts", "status": "modified"},
    {"path": "packages/core/src/new.ts", "status": "renamed", "old_path": "packages/core/src/old.ts"}
  ]
}
```

`status` is `modified`, `added`, `deleted` or `renamed`. `head` is informational. Uncommitted changes appear as ordinary entries relative to `baseline` (section 11.7).

### 9.6 Plan

```json
{
  "protocol": 1,
  "baseline": "9f2c1ab4e0d7c3a1b2c3d4e5f60718293a4b5c6d",
  "graph_version": "g_8f3a21c9",
  "verify": false,
  "tasks": [
    {"id": "packages/core/src/math.test.ts",
     "reasons": ["reads:packages/core/src/math.ts", "self_changed"]}
  ],
  "unobserved": ["README.md"],
  "ignored": [],
  "deleted_tasks": [],
  "total_tasks": 12000,
  "skipped": 11998,
  "fallback": null,
  "confidence": "medium"
}
```

- `tasks` lists the invalid tasks, sorted by id, with sorted reasons.
- With a fallback: `fallback` is `{"action": "run_all", "reason": "<code>"}`, `tasks` lists every known task with reason `["fallback"]`, `skipped` is 0, and `confidence` is `n/a`.
- `skipped = total_tasks - |tasks|`.

### 9.7 Errors

| Code | Meaning | Exit code (CLI) |
|---|---|---|
| `invalid_params` | Malformed request or schema violation | 2 |
| `unknown_method` | Method not in v1 | 2 |
| `protocol_mismatch` | Client protocol not supported | 2 |
| `store_missing` | No store at the path | 3 |
| `store_corrupt` | Log record invalid (not a truncated tail) | 3 |
| `lock_busy` | Another writer holds the lock | 5 |
| `baseline_conflict` | `advance` expected value mismatch | 6 |
| `timeout` | Request exceeded the server budget (10 s) | 4 |
| `internal` | Unexpected failure | 4 |

A fallback is never an error. Exit 0 with `fallback` set is the normal outcome of an unsafe-to-skip query.

### 9.8 Timeouts and budgets

Each request has a 10-second server-side budget. Exceeding it returns `timeout` with `data.partial: false`. The server never returns a partial plan.

### 9.9 Versioning

`protocol` is an integer. Adding a method or an optional field is compatible within a major version. Removing or changing a field's meaning bumps the major version (D-13). The conformance suite has a case for each rule (C34).

## 10. Public API and bindings

### 10.1 Node/TypeScript (first-class binding)

Package `@backplane/client` (name per section 1.4). It spawns `backplane serve`, or connects to a given command, and exposes:

```ts
export interface backplane {
  readonly protocol: 1;
  hello(): Promise<Hello>;
  observe(obs: Observation): Promise<{ accepted: true }>;
  observeMany(obs: Observation[]): Promise<{ accepted: number }>;
  baseline(): Promise<{ baseline: string | null }>;
  advance(to: string, expected: string | null): Promise<{ baseline: string }>;
  affected(changes: ChangeSet, options: AffectedOptions): Promise<Plan>;
  explain(task: string): Promise<Explanation>;
  forget(task: string): Promise<{ forgotten: true }>;
  stats(): Promise<Stats>;
  compact(): Promise<CompactResult>;
  close(): Promise<void>;
}

export function connect(opts?: ConnectOptions): Promise<backplane>;

export interface ConnectOptions {
  store?: string;                 // default: $BACKPLANE_STORE, then <repo>/.backplane
  command?: string[];             // default: ["backplane", "serve"]
  timeoutMs?: number;             // per request, default 10000
  restart?: boolean;              // restart the server if it dies, default true
}

export interface AffectedOptions {
  baseline: string;
  context: Context;               // required (P0b)
  verify?: boolean;               // default false
  policy?: "balanced" | "conservative";  // default "balanced"
}
```

Behavior the client MUST implement:

- Matches responses by `id`, enforces timeouts, and restarts the server if it dies (with `restart: true`). A restart re-runs `hello`.
- Rejects with a typed `backplaneError` carrying `code` and `data`. It never resolves to a partial plan.
- Serializes writes to the server. Concurrent calls are queued in order.

### 10.2 CLI

Binary `backplane`:

```
backplane init     [--store PATH]
backplane observe  --file FILE|-                        # one observation as JSON
backplane affected --changes FILE|- --baseline SHA --context FILE
                  [--verify] [--policy balanced|conservative]
backplane advance  --to SHA --expected SHA|null
backplane explain  --task ID
backplane forget   --task ID
backplane stats    [--json]
backplane compact
backplane serve    [--store PATH]                       # protocol over stdio
backplane version
```

The CLI is a thin binding: every command maps to one protocol method. `--store` defaults to `$BACKPLANE_STORE`, then `<repo>/.backplane`. Exit codes follow section 9.7. Errors print `{"ok": false, "error": {"code": "...", "message": "..."}}` on stdout and a one-line message on stderr.

### 10.3 Python binding (later, E9)

Package `backplane` on PyPI, same protocol and method names in snake_case (`observe_many`, `advance`, `affected`). Uses the same conformance cases. Its API is specified in `spec/bindings-python.md` when E9 starts, not before.

### 10.4 Adapter loop contract

Any adapter that runs tasks MUST follow this loop, and the conformance suite checks it with the Vitest adapter (E4):

```
B   = backplane baseline
ch  = changes from B to the worktree (git change source, 11.7)
plan = backplane affected --baseline B --changes ch --context ctx
for each task in plan.deleted_tasks:  backplane forget
run each task in plan.tasks while recording an observation
if every task in plan.tasks ran and the worktree is clean and HEAD is unchanged:
    backplane advance --to HEAD --expected B
else:
    do not advance; report why; exit with code 7
```

Exit code 7 means "ran, but the baseline was not advanced". It is distinct from a failure, so CI can see it.

## 11. Adapters

### 11.1 Recorder contract

Any recorder, whatever the tool, produces observations that pass the schema in 9.5 and satisfy:

1. Every input it reports was actually used by the task during the run.
2. Every path is canonical (realpath) and repo-relative with `/` separators.
3. Every hash is computed from the file content at the time it was read.
4. A run it cannot observe completely is recorded with `dirty: true` or with the affected capability set to false, never with missing inputs presented as complete.

### 11.2 Vitest recorder (`adapters/vitest`)

Mechanism, in short. A preload loaded through `NODE_OPTIONS` (`--import` for ESM, `--require` for CJS) wraps the `fs` API in its sync, callback, promise and stream forms: read, open, stat, lstat, access, exists, readdir, realpath, readFile and createReadStream. It also wraps module loading. For environment access it replaces `process.env` with a Proxy recording `get`, `has` and `ownKeys`. Each test file runs in its own forked process (D-12), so the preload's observations belong to exactly one task. The preload writes its observations to `BACKPLANE_TRACE_OUT` at exit.

Specific rules:

- Canonicalize every path with `realpath` before exclude matching and before interning (section 11.4).
- Worker threads (CR-003): if a test file starts `worker_threads`, its observation is recorded `dirty: true` (rule 4 above), so the task reruns on every query. Capabilities stay true for the store, because a per-task capability cannot be expressed through P2 without making every query a context change. Adds stay targeted; no store-wide fallback. The recorder never guesses.
- Dynamic imports and `require` with computed paths are observed by the file wrapper; they are not guessed from source.
- Capability flags `probes`, `dirs` and `env` are set true only if E4 proves each on the fixture.

### 11.3 Vitest planner

Maps a plan to Vitest work:

- Task ids are repo-relative test file paths.
- A plan with a fallback runs every known test file.
- `backplane vitest run [--base REF] [--json] [--all] [--jobs N]` computes the plan, runs the invalid test files with the recorder (in parallel, `N` = CPU count by default), writes JSON results when asked, and then follows the loop in 10.4.
- `--shadow` runs everything, reports what the plan would have skipped, and never advances the baseline on its own. It is for measuring before trusting.

### 11.4 Canonical paths and symlinks

Workspace packages reached through `node_modules` symlinks resolve to their real location. The recorder records the real path, and `exclude` is applied to real paths. The fixture (section 14.1) includes a workspace-symlink shape to prove this (conformance case V07).

### 11.5 Strace recorder (`adapters/strace`, Linux)

```
strace -f -e trace=openat,open,openat2,stat,newfstatat,statx,access,faccessat,faccessat2,getdents64,readlink,readlinkat,execve -o <file> -- <cmd>
```

Parses successful read opens (files), directory reads (dirs) and ENOENT lookups (probes) under `roots`, after realpath. It cannot see environment reads.

Rule: the Node recorder MUST contain every path the strace oracle sees, after exclude and realpath. Gaps are recorder bugs. Fix them, or set the capability false and log it in `FRICTION.md`. **Oracle gaps can never be waived.** Environment completeness is checked against the fixture's `expected` file instead (section 14.1).

### 11.6 Adapter loop and its failure modes

| Failure | Behavior |
|---|---|
| Recorder crashes mid-run | Observation recorded with `outcome: "error"`, not advanced |
| Task run times out | `outcome: "error"`, not advanced |
| Worktree dirty at end of run | Observations `dirty: true`, not advanced |
| Baseline conflict on advance | Exit 6, nothing written |
| Shallow clone cannot reach `B` | Adapter runs everything, says so, and does not advance unless the run was complete |

### 11.7 Git change source (`adapters/git`)

Produces ChangeSets:

- Committed and staged changes from `B`: `git diff --name-status -M B`.
- Untracked files: `git ls-files --others --exclude-standard`, as `added`.
- Renames: via `-M`, reported as `renamed` with `old_path`.
- Requires a git repository. Non-git repositories are unsupported in v1.
- Shallow clones: if the history needed to reach `B` is missing, the source MUST fail with `invalid_params` and a message, not return a partial ChangeSet. The adapter then runs everything and says so (section 11.6).

### 11.8 MCP server (`mcp/`, E8)

Tools exposed over MCP stdio, using the official MCP TypeScript SDK pinned in section 15 (E8):

| Tool | Input | Output |
|---|---|---|
| `affected_tasks` | `{verify?}`. The adapter builds the ChangeSet from git and passes context | Plan |
| `record_observation` | Observation | `{accepted}` |
| `engine_status` | none | Stats |

Tool descriptions are one sentence each. The server MUST send context and baseline on every query, so `context_missing` never fires through MCP in normal use.

### 12.5 Replay (false-skip measurement)

1. Take the last N commits on the main line (N = 200 if available; the gate needs at least 50 evaluated commits).
2. In a `git worktree`, check out the oldest commit, observe every task (initial graph), and advance the baseline to it.
3. For each commit `c_i` in order, processing **every** commit so the baseline invariant holds:
   a. ChangeSet from `c_{i-1}` to `c_i`. Baseline `c_{i-1}`, which equals the store baseline.
   b. Plan. Run the invalid tasks while recording. Advance to `c_i`.
   c. **Ground truth** is a separate plain run of the whole suite at `c_i`, with no recorder. It does not change the store.
   d. Evaluate the commit only if the ground truth at `c_{i-1}` was green. Otherwise process it for the baseline but do not count it.
4. A **false skip** is a task that fails in ground truth at `c_i`, was not invalidated by the plan at `c_i`, and fails again on two reruns. Tasks that pass on rerun are flaky and counted separately.
5. Report each false skip with the commit, the task, and the plan's reasons for the other tasks in that query.
6. Report commits processed, commits evaluated, task-commit pairs examined, false skips, and the rule-of-three bound.

### 12.6 Statistics

- **Latency (M1, M2, M11).** A run is 100 queries (M1) or one process invocation (M2). 5 warmup runs, 30 measured runs. Percentiles use every query in the measured runs (3,000 for M1).
- **Other metrics.** 5 warmup and 30 measured repetitions. Report median, p95, and min and max.
- **Zero events.** When a rate of zero is observed in `n` independent observations, publish the 95% upper bound `3/n` next to the zero.

### 12.7 Method

Record CPU, RAM, OS, kernel, Node version, engine version, the container image digest and `arch` for every run. Numbers from different architectures are never compared. Results go to `benchmarks/results/*.json` (schema-validated) and a generated `RESULTS.md`.

## 13. Gates

Decided before any measurement, evaluated by `make gate` or `make gate0`. A failure stops the project (section 14).

### 13.1 Gate 0: the kill test (after E4, before E5)

Run on one real, slow Vitest monorepo chosen by the human, using the replay in 12.5 for at least 50 evaluated commits, or as many as the repo has.

| # | Criterion | Threshold |
|---|---|---|
| K1 | Median share of test files skipped on typical commits (at most 5 source files changed, no global input) | At least 30% |
| K2 | False skips | Zero observed, with the rule-of-three bound reported |
| K3 | Plan latency, cold CLI | Under 1 s |
| K4 | Result compared with the repo's existing selection (Vitest `--changed`, or the team's affected command) | The engine must skip at least 10 percentage points more, or explain each extra run it avoided (no claim without numbers) |

Decision: **CONTINUE** if K1 to K3 pass and K4 shows a real gain. **STOP** otherwise. A STOP is a valid, reported outcome, not a failure of the process.

### 13.2 Gate 1: the full gate (E7)

| # | Criterion | Threshold |
|---|---|---|
| G1 | Typical edits on the chosen corpus: median skip share | At least 50% |
| G2 | False skips over the replay | Zero observed over at least 50 evaluated commits, with the bound reported |
| G3 | Warm plan p99 at 100k tasks, verify off | Under 20 ms |

## 14. Stop conditions and escalation

### 14.1 Stop and report to the human when

- Gate 0 returns STOP, or Gate 1 fails on any criterion.
- A required capability for the Vitest recorder cannot be observed after two different approaches.
- `COMPETITORS.md` shows an existing tool that already provides all of: runtime-recorded dependencies for Vitest, a stable protocol, and sound skips with reason codes. Judgment calls are reported, not decided silently.
- Fewer than 50 evaluated commits can be obtained for the replay.
- The spec is ambiguous in a way that would change a protocol message, a log record, or a plan shape. Write a change request first if the ambiguity is small; stop if it changes a shape.
- The core passes 8,000 lines.
- Anything needs credentials, a paid service, software installed outside the repo, or a Linux container runtime that stops working (Appendix A).
- Two milestones in a row fail sign-off.
- A check fails and the cause is not in the code under test (for example, a conformance case is wrong). Report it; do not edit the case.

### 14.2 Core language ladder

1. TypeScript (default, D-14).
2. If the human chooses Goose for the core, it MUST pass the same conformance suite and G6 before it replaces TypeScript. Goose-specific blockers are logged in `friction/FRICTION.md` and handled with `extern fn` plus a sidecar C file, per Appendix D.
3. Never switch the core language on your own. A switch is a human decision.

### 14.3 Escalation message (exact)

```
STOP: <condition from section 14.1>
Milestone: <id, state>
Done so far: <milestones with evidence files>
What failed: <command, exact output (last 20 lines), what was tried>
Options: A) ...  B) ...  C) ...
Recommendation: <one option and why>
```

Write this in the chat and as a row note in your status file, then end the turn.

## 18. Risks

| Risk | Mitigation |
|---|---|
| False skips destroy trust | Certificate principle (3.3), baseline invariant (3.4), P0 to P2 fallbacks, dirty observations (P8), recorder completeness (11.5), differential fuzz (G5), replay with the rule-of-three bound (12.5), shadow mode (11.3) |
| Non-file inputs (time, network, randomness) | Stated limit (9.6); failed tasks are re-selected (P9); scheduled verify audit |
| Recorder misses probes or dirs | Capability flags false, so balanced falls back on adds; the gate measures the real cost |
| Symlinked workspace packages | Canonical paths (11.4), fixture shape, V07, strace agreement (11.5) |
| Engine is not much better than Vitest `--changed` | Gate 0 K4 compares directly and can stop the project |
| The name is taken or conflicts | Name check in E0 (step 1); single-place rename (10.5) |
| Protocol drift between bindings | Conformance suite is the spec; G6 parity; protocol version negotiation (9.2) |
| Core language risk | TypeScript default (D-14); the Goose track is optional and gated by the same suite |
| Shared stores fall back often | D-11 documents it; M8 measures the benefit |
| Competitors (DiffCI, Launchable, Develocity, Datadog) | COMPETITORS.md (E0 step 3); differentiate on soundness evidence, the protocol, and reason codes, not on claims |
| Single-agent mode reduces independence | Specification-first commit ordering (0.3), fresh clone for sign-off (15.3) |
| macOS host, Linux-only checks | Linux arm64 container (`linux-gate`); stop if the container runtime stops working (Appendix A) |
| Scope creep into builds, CI, and runners | Non-goals (1.3); adapters beyond Vitest are later milestones with their own decision |

## Appendix D. Optional Goose track

If the human chooses to build the core in Goose as well, it is a parallel track, not a replacement:

- Goose facts (documentation level, 2026-11-03): the `os` standard library has file read and write, atomic write and rename, list, env, args, stdin and stdout. It lacks `stat`, exclusive create, realpath, subprocesses and SHA-256; each needs an `extern fn` workaround with a sidecar C file (`foo.build` with `c_sources`). `to_bytes` and `from_bytes` work on arrays only, with the v1 limits listed in the Goose docs. The release v2026.3 has no linux-arm64 build, so the container builds Goose from source.
- The Goose core MUST pass the same conformance suite and G6 parity before it is considered equal to the TypeScript core.
- Milestone DG0: install and identity check (`goose --version`, `goose toolchain`). DG1: spikes for each capability the core needs (file I/O, stat, lock, hashing, JSON, stdin and stdout). DG2: the core against the conformance suite. DG3: benchmarks comparison against the TypeScript core on M1 to M3.
- It is accepted only if it wins on something measured, or if the human wants it for learning. Either reason is recorded in `DECISIONS.md`. Friction goes in `friction/FRICTION.md`.
